## 2. `public/robots.txt` — explicit AI-crawler `Allow` groups

**What changed:** added named `User-agent` groups (each with its own `Allow: /` + the same `Disallow` list as the wildcard) for `Googlebot`, `Google-Extended`, `Bingbot`, `OAI-SearchBot`, `ChatGPT-User`, `GPTBot`, `PerplexityBot`, `ClaudeBot`, `Claude-SearchBot`, and `Applebot-Extended`. Kept `Twitterbot`/`facebookexternalhit` and the wildcard `*` group with its existing `Disallow` list (`/dashboard`, `/dashboard/*`, `/stripe-test`, `/checkout`, `/payment-success`). Kept the `Sitemap:` line.

**Why:** nothing was actually blocked before this change (aeo-plan.md §1.1/seo-technical-audit.md confirm all these bots fell through to the permissive wildcard already) — this is legibility/regression-proofing, not a functional fix. A named, explicit group makes it obvious to any future security-hardening pass that these specific bots are allowed on purpose, instead of "allowed by accident because nobody named them."

**A real behavior change I made beyond the literal ask:** each named bot group also now carries the same `Disallow` lines as the wildcard. The *old* file gave `Googlebot`/`Bingbot`/etc. their own group with **only** `Allow: /` and no disallows — under the robots.txt spec, a crawler matches its *single most specific* group, not a merge of that group + the wildcard. That means, as written before this change, real Googlebot/Bingbot traffic could legally crawl `/checkout`, `/dashboard`, `/stripe-test`, and `/payment-success`, bypassing the disallows entirely. I fixed this for every named group, including the new AI-bot ones, so "keep existing disallows" is actually true for every crawler that matches a specific group, not just for `*`.

**Owner action required (not controllable from this repo):** `docs/metro/research/aeo-plan.md` §3.1 item 6 flags that Cloudflare's dashboard-level **"Block AI Bots"** toggle (under Security → Bots) or **Bot Fight Mode / Super Bot Fight Mode** can silently challenge or block `OAI-SearchBot`, `PerplexityBot`, `ClaudeBot`, etc. at the edge — before they ever reach this robots.txt. **Check the Cloudflare dashboard and confirm these bots are allowed through, not just permitted in robots.txt.** This cannot be verified or fixed from the repo; it requires Cloudflare account access.

## 3. `scripts/generate-sitemap.mjs`

**What changed:**
- **Metro routes added.** New `fetchMetroRoutes()` shells out to a new helper, `scripts/metro/generate-metro-routes.ts` (run via `npx tsx`, since `tsx` can execute the TypeScript metro config directly with no build step and no edits to `src/**`), which imports `METROS` from `src/metro/config` (read-only) and writes `scripts/metro/metro-routes.json`. That JSON currently lists 23 real routes: `/dallas-fort-worth` + its 4 category pages, `/long-island` + its 4 category pages + all 12 of its town pages (`src/metro/config/longIsland.ts`'s `towns` array). DFW's `towns: []` is currently empty in the config, so no DFW town pages exist yet to add — this will pick them up automatically once METRO-CORE populates that array. If `tsx`/the exporter fails for any reason, the script falls back to a small hardcoded `dallas-fort-worth`/`long-island` home-page list rather than losing the metro pages from the sitemap entirely.
- **`/gravel-driveways` hub + spokes** are pulled from `scripts/prerender/extra-routes.json` **only if that file exists** (it's owned by the prerender agent, which is building the hub in parallel — this repo snapshot already has an empty `[]` placeholder there). Nothing about the hub is hardcoded here, per aeo-plan.md's own caution against publishing a reference to content that isn't live yet.
- **`/locations` dropped entirely** from the sitemap (not just the unresolvable slugs — the whole route family). Rationale, in the file's own `DROP_LOCATIONS` comment: seo-technical-audit.md §2.4 shows the sitemap's old source (Supabase `delivery_locations`, ~196 rows) and the page's actual render logic (`LocationPage.tsx`: 28 hardcoded slugs → an unauditable Google Sheet → a 10-entry fallback object → "Location Not Found") are three/four disconnected data sources with nothing keeping them in sync. There is no reliable way, at sitemap-generation time, to tell which of those ~196 URLs will actually render real content vs. soft-404 (HTTP 200 + a client-side redirect after 2 seconds). Rather than guess, I dropped the whole family until either (a) the metro pivot's redirect map is finalized and deployed (`nginx/redirects.conf`, below) or (b) `LocationPage.tsx` is pointed at a single authoritative data source. **This is a judgment call, not an explicit instruction — flag to the METRO-UI/owner if any of the 28 hardcoded-slug pages (e.g. `seattle-wa`, which is confirmed to render real content) should be reinstated in the sitemap before the redirect plan ships.**
- **`/products` and `/product-calculator` dropped** from `STATIC_PAGES` — both are 301'd elsewhere in `nginx/redirects.conf` (to `/shop` and `/calculator` respectively, per seo-technical-audit.md §2.3/§4), so listing them in the sitemap would tell crawlers to discover a URL that immediately redirects away. `/products/:slug` (actual product detail pages) are untouched — they still come from the live `fetchProducts()` Supabase query.
- **3 duplicate blog slugs dropped** (`gravel-vs-crushed-stone-differences`, `10-gravel-driveway-ideas`, `5-gravel-types-guide`) via a `DUPLICATE_BLOG_SLUGS_TO_DROP` set, keeping the canonical half of each pair per seo-technical-audit.md §2.9's placeholder direction. **This direction is still a placeholder** (the audit couldn't determine from code which post in each pair has more real traffic/backlinks) — confirm before treating it as final, then unpublish the loser row in the Supabase `blog_posts` table so it stops re-appearing in the live query.
- **`<lastmod>` is now real, per-page, everywhere it wasn't already:** static pages compute `git log -1 --format=%cI -- <file>` for their actual page component (e.g. `/faq` → `src/pages/FAQ.tsx`), falling back to the file's mtime (for untracked/new files — everything under `src/metro/**` is currently untracked on this branch, so metro routes' lastmod uses file mtime today until this branch is committed) and only to today's date as a last resort. Dynamic pages (products, blog posts, market-material pages) already used real `created_at`/`published_at`/`updated_at` from Supabase — unchanged.
